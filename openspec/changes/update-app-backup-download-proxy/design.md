# 设计：AppBackup 下载代理化

## 背景
当前下载接口返回的是对象存储地址。客户端如果无法直连对象存储，下载会在浏览器侧直接失败。平台需要把下载入口收敛到服务端，由服务端完成对象存储访问、权限校验以及内容转发。

## 目标
- 客户端继续通过一次下载请求拿到可打开的下载地址。
- 下载地址指向平台服务端，而不是对象存储。
- 下载地址失效后，客户端无法继续使用。
- 服务端只在通过下载票据后才开始读取对象存储内容。
- `resource`、`data`、`all` 三种下载类型都走同一套代理入口。

## 非目标
- 不改变 AppBackup 创建、更新、历史查询流程。
- 不把对象存储地址暴露给客户端。
- 不要求前端新增显式下载请求步骤。

## 方案
### 1. 两段式下载流程
下载流程拆成两个阶段：

1. 客户端先请求现有 `/download` 接口。
2. 服务端返回同源下载地址，地址中带有短期有效的下载票据。
3. 客户端打开该地址后，服务端校验票据，再从对象存储读取内容并写回响应体。

这样既保留了现有前端的 `window.open(download_url)` 使用方式，也避免了客户端直连对象存储。

### 2. 下载票据内容
下载票据只描述一次下载请求所需要的最小信息，建议包含以下内容：

- AppBackup 名称
- 备份名称
- 下载类型
- 过期时间
- AppBackup 资源标识
- StorageRepository 资源标识

票据不保存对象存储秘钥，也不保存对象存储地址。票据只负责把浏览器带回服务端的下载入口，真正的读取动作仍然由服务端重新完成。

### 3. 下载流入口
新增一个流式下载入口，供浏览器打开：

- `resource`：读取单个 Velero 资源包对象并直接转发给客户端。
- `data`：读取该备份关联的持久卷数据对象，并按归档流方式输出。
- `all`：读取资源包对象以及持久卷数据对象，并按归档流方式输出。

对于 `data` 与 `all`，服务端不再向客户端返回对象存储对象清单，也不再返回对象存储地址列表，而是直接返回一个可下载的归档流。

### 4. storage 抽象调整
现有 storage 抽象只有生成下载地址与列举对象的能力。下载代理化后，需要新增对象读取与流式转发能力，供 handler 直接把对象内容写入响应体。

建议把对象读取能力放在 storage 层，handler 只负责：

- 校验 AppBackup 是否存在
- 校验历史记录是否匹配
- 校验 StorageRepository 是否存在
- 生成下载票据
- 触发流式下载

### 5. 错误处理
- 票据无效、过期、篡改：返回 403。
- AppBackup 不存在、历史记录不存在、StorageRepository 不存在：返回 404。
- 对象存储读取失败：返回 502。
- 客户端中断下载：立即停止读取并释放资源。

## 决策
- 继续保留现有下载入口路径，减少前端改动。
- 下载地址改为平台服务端地址，不再直接暴露对象存储地址。
- `resource`、`data`、`all` 都通过服务端代理输出，不再让浏览器直连对象存储。
- 下载票据采用短期有效设计，降低链接外泄后的风险。
